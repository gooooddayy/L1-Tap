# 开发笔记：经验与踩坑全记录

> 全部来自真机（OnePlus PJE110 / ColorOS）实测。改 bug 前先读这份，五个根因都踩过一轮。

## 一、五轮 bug 根因（按发现顺序）

### ① 锁点整体偏移：状态栏高度差
- **现象**：连点位置总偏，点到别处
- **根因**：悬浮窗坐标系默认原点在状态栏下方，手势派发用全屏绝对坐标，差一根状态栏高度
- **修复**：窗口加 `FLAG_LAYOUT_IN_SCREEN`（坐标系统一到整屏）+ 锁点改用 `getLocationOnScreen()` 取真实屏幕位置

### ② 启动即死：onInterrupt 误杀
- **现象**：点开始后引擎 30~90ms 内就停（`engine-end reason=null`）
- **根因**：手机共存 GKD/Select to Speak 等无障碍服务，我们一派发手势系统就发 `onInterrupt`，v1.3 把它当"服务被关闭"直接停引擎
- **修复**：**onInterrupt ≠ 服务关闭**，只是事件反馈被临时打断，手势派发能力仍在——只记日志不停引擎；真关闭走 `onDestroy`，派发失败有熔断兜底
- **教训**：无障碍工具必须默认与其他无障碍服务共存，不能假设独占

### ③ 启动竞态自击
- **现象**：修完②后 40ms 内又死
- **根因**：引擎第一击派发只要几毫秒，而 `FLAG_NOT_TOUCHABLE` 在 WindowManager 生效晚 4ms——第一击落进自己的靶标窗口，触发"碰到靶标就停"的保险自杀
- **修复**：startClicking 里**先提交穿透标志 + 置执行态，再启动引擎**（顺序不可颠倒），启动失败回滚
- **教训**：「窗口不可触摸」与「引擎开始派发」之间必须保证 WM 生效次序

### ④ deviceId 过滤误拦真手指
- **现象**：执行中红钮点击、拖动完全无反应
- **根因**：为防自击加了 `deviceId != -1` 过滤（注入事件设备号 -1）——但这台 ColorOS 上**真实触屏事件的 deviceId 也是 -1**，真手指全被拦
- **修复**：删掉 deviceId 判别；红钮改为**无条件停止**（自身连点只落靶标点、锁点已避开设置钮，物理上碰不到红钮）
- **教训**：不要用 deviceId 区分注入/真实触摸，部分 ROM 真实事件同样报虚拟设备号

### ⑤ 高频连点停止通道集体失效
- **现象**：连点时间短+频次高（间隔 < 150ms）时按钮点不动、停不了
- **根因**：防自击的时间豁免窗固定 150ms，间隔一旦小于它就**无缝覆盖全程**，真实触摸全被当成自身连点拦截
- **修复**：豁免窗改"**手势在途（mDispatching）|| 30ms 投递尾差**"——窗长 ~60ms，远小于间隔下限 50ms+30ms 戳长，高频时派发之间必留空档给真实触摸
- **教训**：时间窗豁免在事件高频场景必然失效，要用精确状态（在途标志）而不是固定时长

## 二、ColorOS 真机适配经验

1. **TYPE_TOUCH_INTERACTION_START 不投递**：无障碍服务全程只收到 `TYPE_WINDOW_STATE_CHANGED`。「用户一有操作就停」不能依赖无障碍触摸事件，改用悬浮窗 `FLAG_WATCH_OUTSIDE_TOUCH` 旁听 ACTION_OUTSIDE（不拦截、不影响正常操作，屏幕任意触摸按下都会送来一个事件）
2. **真实触屏 deviceId = -1**：见根因④
3. **Hans 后台清理**：离开前台 ~30 秒进程可能被杀（前台服务也保不住），日志特征 "Hans 冻结管理器"。后果是服务死了连"已完成"通知都没有。缓解：用户回来重开 App 即可（v1.0.0ab 起不再做电池白名单引导——实测不解决强杀）
4. **无障碍服务会被连带关闭**：App 被强制停止/ROM 清理时，已授权的无障碍服务可能掉线。UI 上要做服务状态检测与引导（MainActivity 已有）

## 三、关键机制设计（改代码前必读）

### 窗口触摸策略（核心）
| 状态 | 设置钮窗口 | 靶标窗口 |
|---|---|---|
| 待命 | 可触摸可拖 | 可触摸可拖 |
| 执行 | 可触摸（DOWN 即停） | `FLAG_NOT_TOUCHABLE` 穿透 |

靶标执行期**必须**穿透：否则 Accessibility 手势会被自己的窗口吃掉，连点点自己。

### 防自击三保险
1. 靶标穿透标志**先于**引擎启动提交（根因③）
2. 豁免窗只认"手势在途"（根因⑤）
3. 锁点时避开设置钮位置（靶标物理上碰不到红钮）

### 引擎与 UI 解耦
- `TapService.Params` 构造后不可变，锁点一次快照进 Params，引擎**不回调 UI** 复查坐标（v1.3 的 `setSafeCheck` 双向耦合是历史 bug 温床，已废除）
- 派发非阻塞：`mDispatching` AtomicBoolean 在途标志防堆积，绝不 `await`
- Listener 回调统一 `mMain.post` 切主线程（toast/通知线程安全）

### 靶标变化检测
- 每 500ms 采样：前台包名 + 屏幕方向 + 落点控件特征（类名/ID/文本/边界），与开始时锚点比对
- 锚点防污染：首次采样若 `pkg=null`（共存服务的悬浮层），拿到真实前台包名后**改锚**
- 已知灵敏度权衡：目标 App 内自动轮换的文案也会触发停止（设计上宁可误停不可失控）

### 启动缓冲期
「开始」按钮的触摸事件可能因无障碍事件 ~100ms 投递节流**晚于引擎启动**送达，会被误判为用户触摸。启动后 400~600ms 内的触摸一律豁免（`mArmedAt` / `mStartedAt`）。

## 四、工程注意事项

1. **build.sh 判定必须 `grep -q BUILD_OK`**：javac 偶发崩溃时输出 "error report file"，`grep -E "BUILD_OK|error"` 会误匹配放行旧包装机（实际踩过两次）
2. **改核心代码后必须复核**：曾发生 Edit 误删 `mMain.post` 行，靠 `sed` 复核发现
3. **install 报 Success 但包不存在**：偶发，重装一次即可，装完用 `pm path` 验证
4. **无 Gradle 流水线**：aapt2 compile → link+R.java → javac → d8 → align → sign → verify，版本号在 build.sh 的 `--version-code/--version-name` 和 build.gradle 两处
5. **图标**：`gen_icon.py` 生成 mipmap 五档 ic_launcher.png

## 六、v1.0.1 修复：按返回不停 + 无障碍反复重开（2026-10-13）

### 问题 1：执行中按返回，目标变了但依然在点击
- **根因**：旧版唯一的「靶标变化」检测是每 500ms 采样比对，且**两边都非空才比对**。按返回后同应用内换页 → 包名不变；新页面落点取不到控件节点（整屏视频/图片/游戏）→ 比对被整段跳过，完全漏检。且引擎从不监听「返回键」本身。
- **修复三层**（互不依赖，一层失效还有兜底）：
  1. **按键层**：`onKeyEvent` 监听返回/主页/多任务（config xml 加 `canRequestFilterKeyEvents="true"` + 运行时 `FLAG_REQUEST_FILTER_KEY_EVENTS`）。**恒 return false 绝不消费按键**，按键照常传给系统。
  2. **页面层**：`TYPE_WINDOW_STATE_CHANGED` 维护「前台包名 + 窗口类名」页面身份，切页/弹窗/键盘即时停。滤掉自身包名与无包名窗口（防共存服务悬浮层污染基线）。
  3. **采样层补洞**：新增 sig-gone 规则（基线有落点特征、当前 root 可读但落点无节点 → 判为变化）；`rootPkg()` 修正可能的字面量 `"null"`。
- 删除死代码 `changed()`（逻辑已内联，带 why 原因标注，日志可直接看到哪一项触发的）。

### 问题 2：无障碍服务每次彻底关闭应用后要重新开启
- **机制**：ColorOS 省电策略（Hans 冻结管理器）在前台离开约 30s 后杀进程（此前日志实锤）；进程死 → 其中的无障碍服务死。App 无法阻止被强杀（安卓安全设计），只能降低概率 + 给明确恢复路径。
- **处置**：主界面新增「③ 后台运行保障」卡：`isIgnoringBatteryOptimizations` 状态 + `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 一键申请（异常回退应用详情页）；文案含 ColorOS 手动路径与「被清理后打开一次应用即可自动恢复」。
- 清单新增 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 权限。

### 本版停止通道全景
见 `docs/停止场景与触发判定.md`（A 用户主动 9 条 / B 目标变化 6 条 / C 环境被动 6 条，逐条标注实测状态）。

## 七、v1.0.0ab 修复：回退按键层 + 「点开始后不点击」根治（2026-10-13）

### 用户要求的回退
1. **按键过滤整体移除**（判定副作用得不偿失）：删 `onKeyEvent` + `FLAG_REQUEST_FILTER_KEY_EVENTS`
   + config `canRequestFilterKeyEvents`。该能力在部分 ROM 上会干扰手势派发链路；「返回」在
   手势导航下产生触摸与窗口事件，页面层 + 触摸旁听两条通道已覆盖，无需按键层。
2. **后台运行保障卡移除**（判定没用）：删 MainActivity ③ 卡与 manifest 电池白名单权限。
   遗留事实：ColorOS 强杀无法由应用阻止，被清理后重开 App 即恢复。
3. **权限卡「已开启」按钮不再禁用**：已开启后点击同样进入系统设置页（悬浮窗/无障碍），
   文案改「已开启 ▸」提示可点——此前禁用导致用户无法从应用内进入设置关闭/调整。

### 问题：点击逻辑被改坏 —— 「点开始后不点击」（aa 回归）
aa 引入三个叠加机制，本版逐一修复：

- **机制 A｜豁免窗过窄**：aa 把自身手势豁免窗从 150ms 收敛为「在途 + 30ms 尾差」，
  但无障碍事件投递本身有 ~100ms 节流，注入点击产生的触摸事件常在 60ms 窗后才送达
  → 被误判为用户触摸 → 引擎自杀。**修复：尾差 30→120ms（总窗 150ms）。**
- **机制 B｜派发标志无兜底（主根因）**：aa 让「手势在途时立即停止」成为高频（按键/页面/
  采样即时 stop），个别 ROM 下被中断手势的 onCompleted/onCancelled 不回调 →
  `mDispatching` 永久卡 true → 此后每次 tapAt 直接跳过 =「引擎在跑但一次不点」且不可逆。
  **修复三件套：① 看门狗（派发后 >200ms 无回调强制解锁，下一击自愈）；② startTap 会话级
  复位；③ 移除按键层（减少即时打断诱因）。**
- **机制 C｜输入法窗口污染页面锚**：设置参数时键盘弹出，`mPagePkg` 被更新为输入法包名；
  点「开始」据此锚定 → 键盘收起/焦点回 App 的窗口事件一到即判「页面变化」而停止。
  **修复：输入法包名（`getEnabledInputMethodList` 懒加载）的窗口事件直接过滤。**
- **附修**：页面层类名比对笔误 `!c.equals(mPageCls)`（mPageCls 刚被赋值 → 恒 false）
  → `mBasePageCls`，恢复「同应用换页即停」能力。

### 教训
1. **时间窗收窄必须对照"最慢投递路径"算总延迟**（无障碍事件跨进程 + ~100ms 节流），
   不能按内存路径的毫秒级直觉设定。
2. **任何"一次性状态标志"（如派发在途）都必须有超时兜底**——回调可能永远不来，
   卡死后功能静默失效且不可逆，是最难排查的一类 bug。
3. **"最后事件"不等于"当前状态"**：用事件流维护的页面身份会被输入法等非页面窗口污染，
   过滤要按"来源类别"做（输入法列表），不能靠包名黑名单硬编码。

## 七、v1.0.0ac：「只点 1 次 + 界面卡执行态」双 bug（2026-10-13）

真机日志实锤（网易云播放页，iv=1000ms taps=5 rounds=1）：
- `14:38:13.485 startTap` → `14:38:14.902 page-changed: PlayerActivity -> android.widget.FrameLayout`
  → `engine-end reason=target`：**1.4 秒即被误杀，只点 1 次**。
- `14:38:35.395 btn-down: running -> STOP`：引擎早已结束但 **UI 20 秒仍显示执行态**，用户手点红钮才停。

### 根因（对照 GitHub 上能用的 v1.0.0 逐行 diff 得出；OverlayService 零差异）
1. **页面层按类名比对页面身份**（aa 新增，v1.0.0 无此层）。同应用内的弹窗/菜单/弹层
   类名五花八门（播放页弹个普通弹层类名就是 FrameLayout），被判成「换页」→ 误杀。
2. **外部线程调 stopTap(reason) 清空 mWorker** → worker finally 里
   `mWorker == Thread.currentThread()` 判定失败 → onFinished 回调不投递 → UI 卡执行态。
   v1.0.0 所有停止都在 worker 线程内部 break outer，不经过 stopTap，所以从没暴露。

### 修复
1. 页面层**只比包名**（`!p.equals(mBasePagePkg)`），忽略 com.android.systemui；
   同应用内换页由采样层（sig/sig-gone）兜底——这才是落点级别的真通道。
2. stopTap 不再清 mWorker（新一轮 startTap 覆盖 mWorker，旧 worker 身份不符自动跳过）。

### 经验
- **同应用窗口事件不可当页面身份**：类名维度噪声极大，页面判定只能到包名粒度；
  更细的"内容变化"交给落点采样。
- **外部线程停止 + worker 自检身份 = 回调丢失**：停止入口一多，谁负责投递结束回调
  必须唯一（worker finally），身份锚不能被停止方破坏。

## 八、v1.0.0ad：高频连点下「触摸即停」集体失灵（2026-10-13）

用户实测（5Hz，iv=200ms taps=50 rounds=2，网易云）：触摸靶控件/屏幕其他位置有时不停止、
侧滑返回不停止。红钮与通知栏始终可靠（无豁免窗的通道全数正常）。

### 根因（日志 logcat-1013-1505.txt 实锤）
1. **时间豁免窗吞掉真实触摸**：每次注入点击设 150ms 豁免窗（戳长 30 + 尾差 120），
   200ms 间隔下覆盖 75% 时间轴——真实触摸被成片豁免成"自身连点"。频率越高盲区越大，
   200ms 间隔以上触摸通道基本全盲。v1.0.0 注释里"每次派发之间必留空档"的假设在 5Hz 附近已经不成立。
2. **决定性证据被浪费**：用户每次触摸/侧滑，系统都会取消在途注入手势
   （日志必现 `gesture cancelled`，15:03:18.604 正是侧滑瞬间），旧代码只把取消当
   "派发失败计数"，没有停止。

### 修复（与频率无关）
1. **onCancelled → stopTap(R_TOUCH)**：手势被取消 = 真实触摸抢占 = 用户在操作。
   精确、零延迟、不怕高频。宁停不停（若 GKD 等共存服务派发手势导致取消，停也安全）。
2. **ACTION_OUTSIDE 坐标判别**（nearTapPoint）：触摸坐标在锁定落点 ±16dp 内才视为
   自身连点，坐标判别与频率无关；旧时间窗保留为兜底层（防坐标语义在个别 ROM 上有偏差）。

### 经验
- **时间窗豁免是频率耦合的**：任何"以时间窗区分自己人和真触摸"的设计，窗长必须
  远小于最小间隔；间隔参数用户可调到 50ms，窗长 150ms 根本不成立。用"事件因果"
  （手势被抢占=被触摸）或"空间因果"（落点坐标）才与频率解耦。
- 日志里的异常信号（cancel/fails）先问一句"它是不是某个用户动作的确定性证据"，
  别只当失败计数。

## 九、v1.0.0ae：时间窗彻底退场 + 环形监听层（2026-10-13）

ad 实测：点/滑停止概率大增，但触摸屏幕与侧滑返回仍概率性失灵（约一半）。

### 根因
ad 的 ACTION_OUTSIDE 通道保留了时间窗豁免做"兜底"——5Hz 下每次派发后 150ms 内
outside 事件被豁免，而此段手势早已结束、没有取消信号可依赖 → 55% 时间轴盲区。
教训：**坐标判别落地后，时间窗必须彻底移除，"双保险"在这里是"双漏洞"**。

### 本版改动
1. ACTION_OUTSIDE 只剩两类豁免：启动 600ms 缓冲 + 落点 ±80dp（环区/落点）。
   坐标语义双查（getRawX 屏幕绝对 / getX+窗口原点 局部），防个别 ROM 语义偏差导致自停。
2. **环形监听层**（用户需求「抓靶即停+换位」）：执行期在落点周围挂 4 块可触摸矩形拼成
   回字框（外 80dp/孔 22dp）。约束：靶标本体必须保持 FLAG_NOT_TOUCHABLE——否则
   注入点击会落在自己的悬浮窗上而非应用；环层中心留孔让点击穿透。
   - 环内拖过 slop → 引擎立即停（"一拖就停"），靶标跟手走，松手存位（下轮点新位置）；
   - 环内轻点 → 停；
   - 手指在环上时 stopClicking 延迟拆环（mRingTouching），否则拖动中途窗口被拆。
3. 采样 500ms → 250ms（内容/控件移位判停更快）。

### 已知边界
- 中心孔 ±22dp 内的触摸穿透给应用且不触发停止（物理盲区，孔越小越贴近落点）；
- 落点处若 App 只暴露全屏容器（如网易云 ImageSwitcher），容器内部的内容移位拿不到
  节点信息，采样仍可能盲——这是无障碍树的信息边界，非代码缺陷。

## 十三、v1.0.0ai：触摸停止架构重构「海绵层」——从"判别"到"几何"（2026-10-13）

哈希比对 + 6 份日志逐事件取证，完整证据链见 `全版本审查-触摸停止根因与重构方案.md`）定案：

### 定案结论：整条「旁听 + 判别」路线作废
ColorOS 的 ACTION_OUTSIDE 副本在**坐标 / flags / toolType 三个维度全部不可复原**
（系统合成事件，与源头无关）：
- ad 能停靠的是"注入后 150ms 时间窗豁免"的时间接近度兜底（自家副本总在窗内到），不是判别正确；

- ag/ah 加旗标过滤 → 真手副本也带 0x800 → 26 会话 0 触发。
⇒ 真手与注入"同签名"，任何判别都不可能成立。

### 新架构：海绵层（几何判别）
执行期挂 4 块可触摸矩形铺满全屏，仅锁点周围留 **±2dp（≈±7px）小孔**：
- 自动点击只能从孔里穿过 → **摸到海绵 = 100% 用户**，无需任何判别；
- 孔外任意位置 **DOWN 即停**（快于此前所有通道）；锁点 80dp 内额外允许拖动换位
  （超 slop 靶标跟手；非抓靶区滑动不挪靶标——防停止后顺手滑动误改落点）；
- 删除整个 ACTION_OUTSIDE 分支 + FLAG_WATCH_OUTSIDE_TOUCH + 全部过滤条件；
- 点击点正中 ±2dp 为唯一盲区（物理不可区分）；停止那一下触摸被海绵吸收（防误触）。

### 同期修复
- **首击自伤**：靶标 NOT_TOUCHABLE 的 WM 生效有数帧延迟，首击有时被自家靶窗吞掉
  （ah 期 6/8 会话出现 (42,42) 事件）→ TapService 加一次性首击延迟 120ms。
- **监听层滞留**：旧版自然结束后环层留在屏上（onFinished 不拆环），下次触摸才自清 →
  onFinished 补 removeSponge（手指在屏则待抬手再拆）。

### 经验
- **"能观测到" ≠ "能判别"**：副本存在（af 证明投递通畅）、但可观测维度全被洗掉。
  ac→ah 五轮修复都隐含"判别可行"这个未验证前提——应在第一轮就用实验矩阵
  （真手 vs 注入 × 各字段）验证前提，而不是逐字段试错。
- **几何 > 指纹**：当"用户意图"与"系统信号"无法区分时，改架构让"用户在场"变成
  可被物理捕获的事件（摸到孔外的任何地方），比在信号噪音里找指纹可靠一个数量级。
- 屏蔽层做安全通道时，必须同时检查三件事：① 会不会挡住自动点击自身（留孔）；
  ② 会不会挡住自家其他控件（红钮被盖 → 语义由海绵兜住）；③ 停止后的残留行为
  （延迟拆除防吞错、抓靶区门控防误挪）。

## 十七、v1.0.0am：误点真相——不是海绵拦不住，是采样通道提前杀引擎（2026-10-14）

### 现象
al 实测各项停止「都正常」，但停止那一下会误点到应用。用户问：误点无法避免吗？

### 日志取证（13:13~13:14 全部会话）
- 停止原因全部 `reason=target`，**没有一条 sponge-down**——海绵一次都没拦到。
- 每会话只跑 6~12 击（1~2s）就 `roundDone=0` 自停（taps=30/50 根本没跑完）。
- `target-changed(sig): ImageSwitcher|...|0,0,1264,2780 -> TextView|放松时都在听|330,2266,214,49`
  ——锁点附近 ImageSwitcher 与其下层 TextView 随页面刷新**来回抖动**，单次采样差异即停。

### 因果链
sig 抖动 → 采样停引擎（1~2s）→ **海绵随停止拆除** → 用户去摸屏幕 → 触摸直达应用
= 误点。用户体感「点一下就停」实际是 250ms 采样兜底（页面内容因触摸变化）。

### 修复
sig/sig-gone 类变化加稳定确认：连续 3 次采样（~750ms）稳定在同一新状态才判真变化
（`target-probe` 日志记录确认过程）；回到锚状态清计数。ori/pkg 强信号保持立即停。

### 经验
- **多通道并存时，最敏感的通道会抢跑**：它先停了引擎，其他通道（海绵）连出场机会
  都没有，而症状（误点）被归因到最后一个动作（用户触摸）——取证必须看「谁先停的」。
- 采样类判据必须区分「抖动」与「迁移」：单次差异只配记 probe，连续稳定才配停引擎。

   起始锚非 Activity 时首个 Activity 事件改锚（page-rebaseline）。
2. **采样恢复 al 单次差异即停**（换页兜底，≤250ms）。误停副作用不再靠采样自治。
3. **海绵延迟 1.5s 拆除**（scheduleSpongeRemoval）：引擎自动停止后海绵仍在屏，
   停止后短窗口内的触摸被吸收——误点从机制上根治，且不再依赖「采样判得准」。
   手指在海绵上时维持原逻辑（抬手拆）；startClicking/onDestroy 取消挂起拆除。

### 侧滑返回四重保障
海绵 0ms（摸到即停）/ gesture-cancel 0ms / Activity 事件 0ms / 采样 ≤250ms。
al 只有一重（采样），an 四重且互不背锅。

### 诚实的代价
闪烁页面（网易云每日推荐）上采样仍可能 1~2s 误停引擎（与 al 相同）——但海绵
延迟拆除保证绝不误点，重新点开始即可。这是保「换页兜底秒停」的固有代价。

### 经验
- **「把上个版本成功的逻辑搞清楚」应成为修回归的第一步**：本轮从 21.m 备份取出
  al 源码逐行对照，10 分钟定位 am 病灶——比再打日志猜快得多。
- **一条通道身兼两职必然两头翻车**：sig 通道既要「换页秒停」又要「不误停」，
  物理上没有中间档。拆职责（Activity 事件管换页 / 海绵延迟拆除管误点）后各自
  都能拉满。
- **防误点不要依赖判得准，要依赖「停了以后摸不到应用」**：几何吸收 > 信号判别。

## 十九、v1.0.0ao：侧滑返回误触的盲区分析与收窄（2026-10-14）

### 现象
an 实测：侧滑返回会停止，但返回后页面的元素被误触。

### 日志实锤（17:39-17:40 四次侧滑返回）
- `page-changed(act): PlayerActivity -> MainActivity` 全部捕获，engine-end 与事件**同毫秒**
  ——事件到达后 0 击派发，an 通道本身工作正常。
- 误触窗口 = 事件到达前 ~120-190ms 的最后一击：a11y 事件投递延迟 + 换页动画期
  新页窗口已可见可收触摸。锁点 469,2266 正好压住返回后 MainActivity 的
  「欧美热门精选」TextView（330,2262,214,49）——一击即误触。
- 间隙期边缘滑动被 ColorOS 系统层截走（无 cancel、无 sponge-down、无任何事件），
  应用层在「滑动开始」时完全失明——这是盲区存在的结构性原因。

### ao 双闸（收窄，不承诺归零）
1. **systemui 暂停窗**：TYPE_WINDOW_STATE_CHANGED from systemui → 派发暂停 400ms
   （返回手势提示层是 systemui 窗口，手势一开始就停发新击）。不停机——横幅/音量条
   消失后暂停自动解除，代价是节奏错过 1~2 击。
2. **派发前核对**：每击先 getRootInActiveWindow() 比对活动窗口 pkg/Activity 类名，
   变了先停再派——比 a11y 事件投递快一层，盲区从「事件延迟」缩到「root 更新延迟」。

### 附带结论：无障碍「有时不显示」
全量日志 32 个 FATAL 全是 tvbox.osc（L1Box），本应用零崩溃；代码无 disableSelf。
enabled_accessibility_services 只剩 GKD → 开关被掉（重装 adb install -r 会掉开关）。
ColorOS 无障碍列表偶发不刷新/隐藏条目属系统怪癖：重开一次应用、或重启手机后刷新。

> **更正（v1.0.0aq，2026-10-17）**：上面的「系统怪癖」只猜对了一半。真机实测证明不是
> 「列表不刷新」，而是手机「应用速冻」把包 `pm disable` 了——被禁用的包不参与 intent 解析，
> 系统压根扫不到这个服务。详见第二十一节。

### 经验
- **误触排查先量化「事件后还有几击」**：an 四次侧滑事件后都是 0 击，把误触
  从「停止通道失灵」正确定位到「盲区窗最后一击」，避免又去改停止逻辑。
- **修盲区不要动点击语义**（15ms 是用户定的）：收窄靠「提前停 + 暂停发」，
  不靠「拉长点击遮盖间隙」——后者会改变目标 App 收到的点击形态。

## 二十、v1.0.0ap：点赞类场景 1~2 击即停——成功反馈被当靶标变化（2026-10-14）

### 现象
用户报「很大概率错误检测触摸而停止，实际没有触摸」。日志判定：**非触摸误检**——
18:06 五轮会话停止全部 `reason=target`、零 `sponge-down`、零 cancel。

### 日志实锤
锁点是网易云**点赞按钮**，每轮停止前 sig 恰好 +1~2：
```
165赞 → 166赞 → 168赞 → … → 175赞    （位置基本没动，bounds 只抖几 px）
target-changed(sig): TextView|null|165赞|435,2236,142,76 -> TextView|null|166赞|434,2236,143,76
engine-end: natural=false reason=target roundDone=0
```
因果链：点击生效 → 赞数 +1 → 控件文本原地刷新 → sig 采样判「靶标变化」→ 停机。
**停止是点击成功的副作用**——an 恢复的「单次差异即停」把「按钮回应了自己」
也当成了「靶标变了」。

### 修复（几何判定改锚）
- `sameKind(baseSig, sig)`：sig 前两段（类名|ID）一致 = 原地文本/边界刷新
  → 判定为自己点击的生效反馈，**改锚续点**（`target-selfupdate` 日志）；
- 类名/ID 变了（弹层/换页 = 手指下换了别的东西）或 sig-gone → 照旧停止。
- 关键性质：`pointSig`/`findNodeAt` 只返回**包含锁点的最深节点**——sig 非空
  即「仍压着锁点」，几何条件天然满足，无需额外坐标比对。

### 残余风险（诚实边界）
同应用弹层若恰好在锁点位置放一个**同类名同 ID** 的控件（如列表里另一个 TextView），
会被当自更新续点。缓解：Activity 事件通道管换页 + 用户触摸海绵即停（执行期常在）。

### 经验
- **「按钮对自己点击的回应」是 sig 采样的天然误报源**：点赞/计数/计时类控件
  文本必然随成功点击刷新——采样比对必须区分「内容刷新」与「控件更换」，
  类名+ID 才是控件身份，文本/bounds 只是状态。
- 用户描述的症状（"误检测触摸"）≠ 通道真相（reason=target）：先看停止原因
  字段再下结论，症状归因要过日志。

## 二十一、v1.0.0aq：无障碍列表「有时看不到 / 要开一会儿」——不是刷新慢，是「应用速冻」（2026-10-17）

### 现象
用户报：无障碍列表里总要把应用开一会儿、有时反复进退两次才看得到 L1Tap。
上一轮（十九节）把这归为「ColorOS 列表刷新怪癖」，本轮真机实测推翻。

### 实测证据（PJE110 / ColorOS 14 / Android 14，间隔数秒同一台机）

| 观测点 | 打开应用前 | `am start` 打开一次后 |
|---|---|---|
| `pm list packages -d`（被禁用） | **含 com.l1.autoclicker** | 不含 |
| 包状态 | `enabled=2`(DISABLED) `stopped=true` | `enabled=1`(ENABLED) `stopped=false` |
| `query-services -a ...AccessibilityService` | 21 个服务，**无 L1Tap** | 出现 `com.l1.autoclicker/.TapService` |
| `dumpsys accessibility` installedServiceCount | **20** | **21** |

### 根因
ColorOS「应用速冻」把包置为 `COMPONENT_ENABLED_STATE_DISABLED`（等价 `pm disable`）。
**被禁用的包不参与 intent 解析**：`queryIntentServices` 收不到 →
`AccessibilityManagerService.mInstalledServices` 里没有 TapService →
设置「已下载的应用」里**根本不存在这个条目**（不是排序靠后、也不是加载慢，是压根没这一项）。
点图标 / `am start` 会先解冻（enabled 2→1），系统收到包变更后重建列表，条目才出现。

- 该机 disabled 包共 33 个（含 GMS、多家银行）→ 符合速冻特征；应用 10-14 最后使用，三天未用被冻。
- `pm enable` / `cmd package enable` 被 ROM 拦：`SecurityException: Shell cannot change
  component state for null to 1`；**只有启动应用本身能解冻**。

### 排除的两条（都做过实测，别再走回头路）
1. `android:exported="false"` **不影响**收录与绑定：解冻后立即被 `query-services` 收录，
   历史版本一直能正常 bind。清单未改。
2. `android.settings.ACCESSIBILITY_DETAILS_SETTINGS` 深链**不可用**：ColorOS 14 的
   `com.android.settings/.Settings$AccessibilityDetailsSettingsActivity` 受签名权限
   `android.permission.OPEN_ACCESSIBILITY_DETAILS_SETTINGS` 保护，三方应用调用必抛
   SecurityException（未 catch 直接崩）。

### 处置
- 主界面无障碍卡三态：`✔已开启` / `✘未开启`（给进入路径）/ `⚠系统待刷新`（解冻后
  1~2 秒窗口，3s×12 轮询自愈，不用退出再进）。
- 使用说明加「无障碍列表里找不到 L1Tap？」排障两条；新清单 `docs/测试清单-v1.0.0aq.md`。
- 应用侧**无法自救**：包被 disable 时代码压根不运行。只能引导用户启动一次解冻，
  并把 L1Tap 加入速冻白名单（设置 → 电池 → 应用速冻）。

### 经验
- **「应用被禁用」在系统里是静默失败**：无障碍列表、包解析、启动全部「正常」，
  只是那个包对别人不存在。查「列表里没有本应用」先跑 `pm list packages -d`，比读代码快一百倍。
- 排查顺序应是「系统侧状态」→「应用侧代码」：本次两张 dumpsys 表的对话，比读 40KB 源码更早给出答案。
- 三方应用**没有任何 API** 能直接打开某个无障碍服务的详情页；网上的
  `ACTION_ACCESSIBILITY_DETAILS_SETTINGS` 片段在 Android 12+ 上必崩，别照抄。
